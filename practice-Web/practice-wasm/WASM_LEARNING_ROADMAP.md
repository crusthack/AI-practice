# WebAssembly Learning Roadmap

## Current Scope

This workspace starts with small examples that make WebAssembly visible instead of hiding it behind a framework. The path is intentionally staged:

| Stage | Project | Focus | Output |
| --- | --- | --- | --- |
| 0 | `00-js-raw-module` | WebAssembly binary loading | Browser page calling `add(a, b)` |
| 1 | `01-wat-add` | WAT text format | `.wat` source compiled to `.wasm` |
| 2 | `02-memory-from-js` | Linear memory | JavaScript writes memory, WASM reads it |
| 3 | `03-rust-wasm-bindgen` | Rust browser interop | Rust functions callable from JS |
| 4 | `04-c-wasi-cli` | WASI CLI model | Sandbox-friendly command-line module |
| 5 | `05-browser-canvas` | Browser computation | Pixel data generated by WASM |

## Phase 1. Runtime Fundamentals

Learning goals:

- Distinguish module, instance, memory, table, import, and export.
- Use `WebAssembly.Module`, `WebAssembly.Instance`, and `WebAssembly.instantiate`.
- Understand why WebAssembly cannot access the DOM directly.
- Treat JavaScript as the browser host environment.

Practice:

- Instantiate a module from bytes.
- Print exported function names.
- Call exported functions with different integer inputs.
- Add a host import and call it from WebAssembly in a later WAT module.

## Phase 2. WAT and the Stack Machine

Learning goals:

- Read WebAssembly Text Format.
- Understand `i32`, `i64`, `f32`, and `f64`.
- Follow stack-based instructions such as `local.get`, `i32.add`, and `call`.
- Compile WAT to WASM with `wat2wasm`.

Practice:

- Modify `add.wat` to add `sub`, `mul`, and `max`.
- Export multiple functions from one module.
- Intentionally break a type signature and inspect the validation error.

## Phase 3. Linear Memory

Learning goals:

- Understand WebAssembly linear memory as a growable byte array.
- Use `ArrayBuffer`, `Uint8Array`, and `DataView` from JavaScript.
- Learn pointer-and-length conventions.
- Avoid assuming WebAssembly has direct access to JavaScript objects.

Practice:

- Write numbers into memory from JavaScript.
- Read and sum those numbers from WebAssembly.
- Return an offset and length instead of returning a string object.

## Phase 4. Rust to WebAssembly

Learning goals:

- Build Rust for the browser with `wasm-pack`.
- Use `wasm-bindgen` for ergonomic JavaScript bindings.
- Know what glue JavaScript does.
- Keep exported APIs small and explicit.

Practice:

- Export numeric functions first.
- Add string input/output.
- Inspect generated package files.
- Compare debug and release builds.

## Phase 5. WASI

Learning goals:

- Understand WASI as a system interface outside the browser.
- Learn the difference between browser host APIs and WASI host APIs.
- Use preopened directories and environment variables deliberately.
- Treat WASI as sandboxed native-style execution.

Practice:

- Compile a C CLI program to `wasm32-wasi`.
- Run it with a WASI runtime.
- Read command-line arguments.
- Try file access with and without preopened directories.

## Phase 6. Browser Computation Project

Learning goals:

- Use WebAssembly for compute-heavy work while keeping rendering in JavaScript.
- Pass pixel buffers across linear memory.
- Keep DOM/canvas calls on the JavaScript side.
- Measure before assuming WebAssembly is faster.

Practice:

- Fill an RGBA buffer in WebAssembly.
- Copy it into a Canvas `ImageData`.
- Add a JavaScript implementation and compare frame time.

## Long-Term Topics

| Topic | Why it matters |
| --- | --- |
| Component Model | Future-facing module composition and interface types |
| WASI Preview 2 | Newer capability-oriented WASI APIs |
| Emscripten | Mature C/C++ browser toolchain |
| Threads and SIMD | Performance-sensitive browser and runtime workloads |
| Debugging | Source maps, browser devtools, and runtime tracing |
| Security | Sandboxing, capabilities, and host boundary design |
| Performance | Startup time, call overhead, memory copies, and binary size |
